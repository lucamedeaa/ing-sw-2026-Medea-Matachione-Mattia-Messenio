This sequence diagram shows what happens when a player takes a card during the game. The
client is already in an active match. The player clicks a card on the board, and the game
view calls takeCard(row, col) on the ServerProxy. The proxy sends a TakeCardMessage through
the socket connection. On the server, SocketClientHandler receives the message and
dispatches it to the ConnectionSession.

The session forwards the command to its current state. Since the player is in game, the
active state is InGameConnectionState. This state adds the player nickname to the request
and calls handleTakeCard on the GameController. The controller submits the operation to the
single game executor used by the match, so the move is not executed on the network thread.

The model receives the command as takeCard(nickname, row, col) and delegates it to the
current game state. The state can be ActionState, during the normal action phase, or
AdditionalPickState, during bonus picks. The state checks that the player is the active
player and that the selected card can be taken. It also checks row restrictions, remaining
picks, card type, and food cost according to the current phase. If one of these checks
fails, an InvalidGameActionException is thrown. The controller catches it, calls the error
callback, and the client receives an ErrorMessage. The client notification controller then
stores the error in the GameModel and shows it in the game view.

If the move is valid, the state removes the card from the board, applies its cost, adds it
to the player's tribe, and pushes the related events into the model. The event batch may
include CardTaken, PlayerResourcesChanged, and CardAddedToTribe. Depending on the result of
the move, it may also include events such as TotemReturned, BoardRefilled, RoundAdvanced, or
EraTransition, when the turn, round, or era advances.

After the state has finished updating the model, the controller calls commitEvents(). The
model publishes the collected events to every registered VirtualView as a single
ModelUpdate. Each VirtualView converts the update to DTOs and filters the available actions.
Only the active player receives non-empty actions; the other clients receive the same events
with an empty action list.

The server sends the update as a DeltaEventMessage. On the client,
ClientNotificationController receives the delta and passes each event DTO to EventApplier.
The applier updates the local GameModel: it removes the selected card from the board,
updates resources, adds the card to the tribe, and applies any extra events generated by the
state transition. After all events have been applied, the controller stores the new
available actions and active player. The model then notifies the UI, and the game view
renders the updated board.
