# Login / Matchmaking

When a player joins, the request crosses every layer while each keeps one responsibility. The view talks only to the abstract `ServerProxy`, so it stays unaware of whether the transport is Socket/TCP or RMI. On the server the handler does not interpret the message; it forwards it through `dispatchTo`, and the State pattern routes it to the active `LobbyConnectionState`. Joining can fail for two distinct reasons, which the nested alternative keeps separate. First the lobby may not locate a valid room (wrong id, game absent, nickname already taken). Only after a room is resolved can the room itself still reject the player, because it filled up or already started in the interval, when `room.addPlayer` raises a `LobbyActionException`.

On success the ordering is significant. The server confirms admission with `matchmakingSuccess` before running side effects through `afterMatchmakingSuccess()`, so a player never observes a broadcast or game start before its own confirmation. When the room reaches capacity, the diagram shows the handoff from matchmaking to live game: each player receives a dedicated `VirtualView`, its connection transitions to `InGameConnectionState`, and the view registers as a model observer. Starting the model then emits a full synchronization rather than an incremental update, because the client holds no prior state, and each view filters that snapshot for its own player before sending it down to render the initial board.
